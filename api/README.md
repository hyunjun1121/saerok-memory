# Haru same-origin data API

These Vercel Functions are a fail-closed foundation for country-separated
collection. They return `503 {"error":"data_plane_unavailable"}` until all
server-only environment variables in `.env.example` are configured. There is
no in-memory or cross-country fallback.

Enrollment sets a 90-day `HttpOnly; Secure; SameSite=Lax` `haru_device` cookie.
Same-origin requests send it automatically; a Bearer device token remains
supported for controlled non-browser clients. Every response sets
`Cache-Control: no-store`. Clients never send `market` or `locale`; the
function derives both from `HARU_MARKET`.

Server-only deployment variables:

- `HARU_MARKET`: `kr` or `jp`; each deployment points to its matching country
  project.
- `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and
  `HARU_ENROLLMENT_CODE_PEPPER`: existing data-plane credentials.
- `HARU_COUNSELOR_API_SECRET`: random 32–256 character credential accepted
  only by the trusted counselor enrollment-code endpoint.
- `CRON_SECRET`: random 32–256 character worker secret. Vercel sends it as the
  `Authorization: Bearer ...` header for scheduled calls.
- `HARU_VOICE_STORAGE_BUCKET`: country-local private bucket containing paths
  referenced by `voice_assets`.

Do not use `VITE_` variants for any server credential.

## Enrollment and consent

`POST /api/internal/v1/counselor/enrollment-codes` issues an eight-character
enrollment code from a trusted counselor service. It requires the exact
`Authorization: Bearer <HARU_COUNSELOR_API_SECRET>` header. Never expose or
call this endpoint directly from the SPA, and never use a `VITE_` variable for
this credential.

The optional body is `{"expiresInMinutes":1440}`. The allowed range is 5 to
10,080 minutes (seven days), and the default is one day. Country comes only
from server-side `HARU_MARKET`; client market overrides are rejected. Success
returns `code`, `participantId`, `market`, and `expiresAt`. Plaintext code is
returned once. Supabase receives only its peppered SHA-256 hash. Code expires
and redemption consumes it atomically once.

`POST /api/enrollment/v1/redeem`

```json
{
  "code": "ABCD2345",
  "installationId": "inst_jp_00112233445566778899aabbccddeeff",
  "consentRevision": "2026-08-01"
}
```

Successful redemption consumes the eight-character code atomically and stores
the device credential only in the HttpOnly cookie:

```json
{
  "participantId": "uuid",
  "market": "jp",
  "locale": "ja-JP"
}
```

Enrollment creates a receipt with every optional grant disabled. Submit a full
snapshot after the user makes a choice:

`POST /api/privacy/v1/consents`

```json
{
  "revision": "2026-08-01",
  "occurredAt": "2026-08-06T00:00:00.000Z",
  "grants": {
    "usageAnalytics": true,
    "longitudinalActivity": true,
    "voiceCapture": false,
    "sttProcessing": false,
    "transcriptStorage": false,
    "audioStorage": false,
    "personalization": false,
    "familySharing": false
  }
}
```

Telemetry needs `usageAnalytics`; activity endpoints need
`longitudinalActivity`. `voiceCapture` is independent from STT processing,
transcript retention, and audio retention. A `voice_capture_status` event needs
both `longitudinalActivity` and `voiceCapture`. Supabase RPCs enforce these
gates again.

## Telemetry

`POST /api/telemetry/v1/batches`

```json
{
  "schemaVersion": "1.0",
  "events": [{
    "schemaVersion": "1.0",
    "eventId": "evt_jp_00112233445566778899aabbccddeeff",
    "eventName": "question_completed",
    "occurredAt": "2026-08-06T00:00:00.000Z",
    "sequence": 4,
    "appVersion": "1.0.0",
    "contentPackVersion": "jp-2026.08.1",
    "installationId": "inst_jp_00112233445566778899aabbccddeeff",
    "visitId": "visit_00112233445566778899aabbccddeeff",
    "routineSessionId": "routine_00112233445566778899aabbccddeeff",
    "questionInstanceId": "question_instance_7",
    "routeId": "/lesson",
    "consentRevision": "2026-08-01",
    "payload": {
      "attemptCount": 1,
      "activeDurationMs": 3210,
      "wallDurationMs": 4010,
      "feedbackDurationMs": 500
    }
  }]
}
```

Maximum: 50 events and 64 KiB serialized JSON per batch. Event names,
top-level keys, payload keys, identifiers, arrays, counts, percentages, and
durations are allowlisted and bounded. Free text, transcripts, raw audio, tap
coordinates, raw key values, `market`, and `locale` are rejected. Event IDs,
installation IDs, and visit IDs follow the prefixes generated by
`src/features/analytics/identity.ts`. `eventId` is the idempotency key. A valid
batch is atomic at the HTTP validation layer; both new rows and duplicates are
returned in `acceptedEventIds`, allowing the outbox to acknowledge retries.
`acceptedCount` and `duplicateCount` are included for diagnostics.
`consent_changed.category` accepts `voice_capture` separately from
`stt_processing`, `transcript_storage`, and `audio_storage`.

## Activity

`POST /api/activity/v1/sessions` accepts:

```json
{
  "sessionId": "routine_00112233445566778899aabbccddeeff",
  "state": "started",
  "occurredAt": "2026-08-06T00:00:00.000Z",
  "contentPackVersion": "jp-2026.08.1",
  "consentRevision": "2026-08-01",
  "progressPercent": 0,
  "activeDurationMs": 0,
  "wallDurationMs": 0
}
```

States: `started`, `paused`, `resumed`, `exit_observed`, `completed`.

`POST /api/activity/v1/question-attempts` accepts IDs, timestamps, active/wall
durations, first-interaction and confirmation latency, plus a bounded response:

```json
{
  "sessionId": "routine_00112233445566778899aabbccddeeff",
  "questionInstanceId": "question_00112233445566778899aabbccddeeff",
  "questionId": "D1_Q1",
  "questionType": "single_choice",
  "contentPackVersion": "jp-2026.08.1",
  "presentedAt": "2026-08-06T00:00:00.000Z",
  "completedAt": "2026-08-06T00:00:04.000Z",
  "activeDurationMs": 3210,
  "wallDurationMs": 4000,
  "firstInteractionMs": 900,
  "confirmationLatencyMs": 1200,
  "response": {
    "selectedOptionIds": ["choice_1"],
    "isCorrect": true,
    "retryCount": 0,
    "hintCount": 0
  }
}
```

Transcripts and media are deliberately not accepted by this endpoint.

## Privacy

- `POST /api/privacy/v1/exports` with `{"format":"json","categories":[...]}`.
  Categories: `profile`, `consents`, `sessions`, `attempts`, `memory`,
  `caregiver`, `telemetry`.
- `POST /api/privacy/v1/deletions` with a client-stable UUID `requestId` and
  categories from `profile`, `activity`, `memory`, `voice`, `caregiver`,
  `telemetry`, or the sole category `all`. Reusing the UUID is idempotent.
- `GET /api/privacy/v1/deletions/:requestId` returns `queued`, `processing`,
  `completed`, or `failed`. Completion of an `all` deletion expires the device
  cookie in that status response.

Creating a deletion job immediately fences later telemetry/activity/memory
writes.

### Deletion worker

`GET /api/internal/v1/deletions/process` is scheduled hourly by `vercel.json`.
It requires the exact `Authorization: Bearer <CRON_SECRET>` header; device
cookies, client-supplied market values, and `VITE_` secrets do not authorize it.
The runtime always supplies its server-side `HARU_MARKET` to each RPC.

Each invocation handles at most five jobs. The claim RPC atomically selects a
due queued job or a processing job stale for 15 minutes, rotates its claim
token, and returns that participant's active voice-object paths only for
`voice`/`all` requests. The worker deletes those exact paths from the configured
Supabase Storage bucket before calling the database finalizer. The finalizer
rechecks the claim token and exact path set, deletes requested database
categories in one transaction, and then records only a minimal completion
receipt and audit event. Partial deletion releases the write fence after
completion; `all` deletes the participant and leaves only the unlinked job
receipt/audit.

Storage or finalization failure never produces `completed`. A valid claim is
requeued for five minutes with a bounded failure code; the fifth failed claim
is marked `failed` for operator review. A crashed worker remains `processing`
until its 15-minute stale window permits a new token-fenced claim. Provider
error bodies, participant IDs, voice paths, and claim tokens are never returned
by the endpoint.

Current limitation: this schema has no external RAG/vector-object inventory,
so the worker can prove deletion only for data represented in this Supabase
schema and its configured voice bucket. Add participant-scoped RAG references
and deletion confirmation before treating external RAG state as covered.
