### 계획 상태와 실행 상태 구분

- 이 문서는 향후 실행 계획이다. `Future task`는 취소가 아니라 다음 작성 턴에서 수행할 작업이라는 뜻이다.
- `Blocked: needs user input`은 로컬 자료나 웹 검색으로 추정하면 안 되는 사용자 제공 정보가 필요하다는 뜻이다.
- 기존 폴더에 초안, 백업, 스크린샷, 로그가 존재하더라도 이번 턴에서는 그것을 최종본으로 확정하지 않는다. 미래 실행자는 반드시 재검증 후 사용한다.
- 이전 작업 기록 중 유용한 요구사항, 구현 근거, 후보 출처, 후보 스크린샷은 이 계획서의 근거 후보로 보존한다.

### 5.2 핵심 의존성 규칙

- 공고/양식 분석(D1) 없이는 섹션별 작성 우선순위를 확정하지 않는다.
- 팀 정보(D2) 없이는 팀 역량 섹션(D10b)을 최종화하지 않는다.
- 영상/후보 이미지 검토(D5)와 라이브 실행(D6) 없이는 최종 이미지 선택(D7)을 확정하지 않는다.
- 구현 기능 검증(D3) 없이는 기능·기술·진행률 주장을 쓰지 않는다.
- 웹 근거(D8a, D8b) 없이는 의료, 돌봄 부담, 사회적 고립, 접근성, 통계, 사업화 맥락 주장을 단정하지 않는다.
- 주장-출처 매핑(D9) 없이는 최종 출처나 각주를 넣지 않는다.
- 개인정보/보안 평가(D4) 없이는 데이터 처리, 공유, 보호자 권한 주장을 쓰지 않는다.
- 최종 검증(D13)은 초안, 이미지, 출처, 팀 증빙, 파일 형식이 정리된 뒤 마지막에 수행한다.

### 9.3 이미지 수용 기준

- 본문 삽입 후에도 핵심 한글 문구가 읽혀야 한다.
- 로딩 화면, 브라우저 크롬 UI, 개발자 도구, 캡처 도구 UI가 들어가지 않아야 한다.
- 지원서 주장과 직접 연결되는 화면만 사용한다.
- 가족 화면은 실제 공유 구현 증거가 아니라 향후 가족지원 진입점으로만 캡션을 단다.
- 설정 화면은 데이터 삭제 흐름을 보여 주되 암호화나 서버 보안 완료 주장으로 연결하지 않는다.

## 14. 상태 관리 규칙

모든 작업은 아래 상태 중 정확히 하나를 사용하고, 반드시 다음 행동을 붙인다.

| 상태 | 의미 | 사용 예 | 다음 행동 작성 원칙 |
|---|---|---|---|
| `Done: this turn` | 이번 계획 보강 턴에서 완료 | `plan.md` 섹션 보강 | 결과와 파일 경로 기록 |
| `Done: evidence already collected` | 현재 로컬 자료에서 이미 근거를 확인 | 공고 심사항목, README 기본 기능 | 미래 작성 전 재확인 여부 기록 |
| `Done: candidate asset exists` | 파일 존재는 확인했지만 최종 사용 전 열람 필요 | `final_*.png` 후보 | 열람/가독성 검증을 다음 행동으로 기록 |
| `Ready for future execution` | 선행 조건이 충족되어 다음 턴에서 바로 수행 가능 | 백업 생성, 코드 재검증 | 실행할 명령이나 파일을 명시 |
| `Future task` | 선행 작업 후 수행할 예정 | 웹 근거, 초안 작성, 최종 검증 | 선행 의존성을 명시 |
| `Blocked: needs user input` | 사용자 사실 없이는 진행하면 위험 | 팀명, 권역, 증빙 | 필요한 질문을 구체화 |
| `Out of scope for this plan-refinement turn` | 이번 턴에서는 하지 않음 | 지원서 작성, HWP 편집 | 수행할 미래 Phase를 명시 |
| `Optional` | 필수는 아니나 품질 향상 가능 | 보조 주제, 추가 사례 | 선택 조건을 명시 |
| `Not applicable` | 현재 프로젝트와 맞지 않음 | 치매 조기 탐지 주제 | 제외 사유 기록 |

금지할 상태 운영:
- 단순히 이번 턴 범위가 아니라는 이유로 `Cancelled`를 쓰지 않는다.
- 사용자 정보가 없는데 임의로 `Done` 처리하지 않는다.
- 과거 기록만 보고 현재 워크트리 검증을 생략하지 않는다.

## 16. 다음 작성 턴 시작 절차

1. 최신 사용자 지시가 지원서 작성 또는 제출본 생성인지 확인한다.
2. `plan.md`의 Scope Lock을 확인하고, 이번 턴 범위를 새로 기록한다.
3. `지원서_양식.txt`를 편집하기 전 새 백업을 만든다.
4. 팀 정보, 제출 권역, NIPA 증빙, 최종 파일 형식을 사용자에게 확인한다.
5. Phase 1과 Phase 2를 재실행해 공고/양식/구현 상태를 최신화한다.
6. Phase 3에서 외부 근거를 원문 기준으로 재확인하고 접근일을 기록한다.
7. Phase 4에서 앱을 실행해 새 스크린샷을 캡처하거나 기존 후보 이미지를 직접 검증한다.

9. Phase 6과 Phase 7에서 한국어 문체, 금지 주장, 주장-출처 매핑을 점검한다.
10. Phase 8에서 분량, 이미지, 증빙, 백업, 최종 형식을 확인하고 결과를 `plan.md`에 기록한다.

### 17.7 완료 판단

- 실행 가능한 작업은 완료했다.
- `지원서_양식.txt`에는 한국어 지원서 초안이 있고, 팀 정보처럼 사용자 제공 사실이 필요한 부분은 표시문으로 남아 있다.
- 화면 자산, 외부 근거, 코드 근거, 검증 명령, 백업, 남은 블로커가 기록되어 있다.
- HWP 제출본과 팀 증빙자료는 사용자 입력 없이는 사실 기반으로 완성할 수 없으므로 `Blocked: needs user input`이다.
- 따라서 현재 패키지 상태는 `제출 전 사용자 정보 보완이 필요한 완성 초안 패키지`이다.
